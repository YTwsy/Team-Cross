# Team Cross Agent Wiki

Agent Wiki 为人和 Agent 提供概念关系、当前工程契约与证据入口，帮助后续工作找到产品约束、相关代码、验证方法及必要的接续信息。`sources/` 与 `wiki/` 描述当前项目，`tasks/` 保存具体工作的过程与证据；任务记录中的临时判断不作为当前项目约束。

从 [任务索引](wiki/index.md) 按修改范围选读。产品概览与公共阅读入口见根目录 [README](../../README.md)，用户操作见 [使用指南](../user-guide.md)，本地开发见 [开发与构建](sources/development.md)。

## 目录与职责

```text
docs/agent-wiki/
├── README.md                       本维护规则
├── sources/
│   ├── development.md              环境、启动与开发调试
│   ├── architecture.md             架构等当前工程事实
│   ├── releasing.md                构建与发布操作、渠道及签名边界
│   ├── decisions/                  当前领域契约与设计取舍
│   └── validation/
│       ├── test-gates.md            当前验证方法与通过标准
│       └── evidence-map.md          已知验证范围及证据入口
├── wiki/
│   ├── index.md                    工程任务导航
│   └── concepts/                   概念、关系、职责边界与来源入口
└── tasks/
    ├── <task-id>.md                 按需创建的活跃任务记录
    └── finished_archived/           已结束记录，默认检索排除
```

图中的任务文件只是示例，不需要预先创建。

- `sources/` 根目录维护项目级规范与操作说明，包括词汇、流程、架构、协议、开发、安装与发布；它们不必归入概念或决策目录。每类事实有一个主要维护位置，重要页面开头说明本页职责及相关来源。
- `sources/decisions/` 维护当前领域契约与设计取舍：规则、适用范围、限制、选择理由和重新评估条件，随所在分支的实现维护。它不是仅保存历史选择的记录库；历史过程留在任务记录。不要求每个领域再拆一份规范或摘要。
- `sources/validation/` 维护验证方法、通过标准与证据范围。`test-gates.md` 回答如何验证；[evidence-map.md](sources/validation/evidence-map.md) 维护具体路径的已知结果、被测版本/环境、证据指针与适用边界，完整执行结果按 [任务记录](#任务记录) 留存。
- `wiki/concepts/` 是理解系统的领域地图，按概念关系组织，并用带用途的链接指向主要来源。具体行为、字段、接口、操作步骤和异常处理由来源维护，验证方法与实际结果分别进入验证契约和证据入口。一个概念页可连接多个来源；来源已清楚、无需额外解释时，由索引直接链接。
- `wiki/index.md` 负责工程任务导航；根目录 [AGENTS.md](../../AGENTS.md) 负责首次进入仓库的阅读顺序和必要行为规则。
- `tasks/` 保存本次目标、临时判断、执行观察和未完成事项；归档记录只说明当时版本与环境下的判断。

当前采用手工维护，没有启用自动 wiki compiler；未来 compiler 的本地状态使用已被 Git 忽略的 `.llmwiki/`。

## 概念页的抽象边界

概念页保留理解系统所需的对象含义、关系与职责边界。例如“已发布材料固定共享依据，个人会话保留各自上下文，共同执行另有输入归属”说明三者的关系；具体发布条件、投递规则和权限检查回到来源查询。

必要时用简单结构图表达包含、依赖、职责或作用域；连线说明含义，文字应能独立解释同一关系。调用顺序、条件分支和恢复步骤留在对应来源，图与文字采用相同的抽象尺度，无须每页套用固定格式。

仅字段、匹配算法或调用实现变化，而概念关系与来源入口未变时，概念页应仍然成立。改写后用一个关系问题检查解释是否清楚，再用一个具体行为问题检查能否沿链接找到规则；同时核对移出的有效约束与证据指针各有去处。

## 事实来源

用户已确认的产品决策确定目标；代码和测试说明当前实际能力。二者不一致时，应明确记录差异并修正相关实现或说明，不能把计划写成已经验收。

[产品核心与词汇](sources/product-core-and-glossary.md) 负责语义，[产品流程](sources/product-flows.md) 负责用户动作，[架构](sources/architecture.md) 负责模块与数据流，[协议](sources/protocol.md) 负责字段与路由，[分发](sources/distribution-and-onboarding.md) 负责安装归属与本机入口，[发布](sources/releasing.md) 负责产物构建和发布操作。领域契约维护具体功能的支持边界，证据入口不另建一份产品支持清单。

原生平台能力、Team Cross 已接入路径和特定环境验收结果分别判断。回答“支持吗、可用吗、是否通过验收”时，先确定目标会话、客户端及传输路径，再核对契约、实现和对应执行记录；测试代码存在、构建成功或模拟协议通过不能补成真实客户端已通过。旧记录须核对后续相关改动，未找到证据时明确区分未检索到、未覆盖与尚未实现。

当前内容以 main 的 Codex 原生协作为基准；旧 Thread、Round、Evidence、managed Bridge、旧 Claude Bridge 和旧传输方案属于历史实现。实验性 Claude 原生 TUI 以 [当前接入契约](sources/decisions/claude-native-tui.md) 为准。需要追溯旧现场时，查看 [迁移记录](../../IMPLEMENTATION.md) 指向的归档提交。

## 更新流程

1. 判断变化是否影响未来任务的产品或工程判断；有影响时更新对应来源，涉及新的取舍时记录原因和重新评估条件。
2. 概念含义、关系、职责边界或来源入口变化时才更新概念页；任务索引、AGENTS 与 README 按各自内容变化更新，不机械刷新所有层级。
3. 按 [验证门槛](sources/validation/test-gates.md) 执行适用检查，将实际结果与未覆盖范围分开记录。新结果扩展范围、暴露阻塞或后续改动影响旧证据时，同步更新证据入口与领域契约中的当前限制；无需给每次普通测试新增条目。
4. 在同一提交中检查相对链接、代码路径、旧引用和索引可达性。精简概念页前核对与来源的差异，将独有且有效的规则、验证要求与证据指针移入对应来源，再移除重复细节。

确定下来的长期知识随开发分支中的代码推进，不集中拖到合入时。恢复既有行为、样式微调等未改变长期知识的工作，不必新增决策或概念页。

Markdown 默认使用简体中文；API、命令、协议字段和代码标识符保持英文。`sources/` 与 `wiki/` 不堆积一次性日志、普通 TODO 或未验证猜测；这些内容确有接续价值时，放进任务记录并明确其状态。凭据和真实邀请 secret 不写入任何文档。文档整理本身不需要启动 Codex、调用模型或打开测试客户端。

## 任务记录

默认不创建任务文件。能在当前对话与代码差异中讲清楚的小改动，在提交或 PR 中简要说明改动与实际检查即可。记录形式取决于中断接续、交接和调查复杂度；验证力度仍按变更风险与验证门槛决定。

| 情况 | 记录方式 |
| --- | --- |
| 状态栏折叠、局部布局或文案调整 | 通常无需任务文件，保留必要检查与交付说明 |
| 跨会话推进，需要保留当前判断和下一步 | 一份 `tasks/<task-id>.md` 即可 |
| 多方案调查或多环境验收，单文件已不便阅读 | 使用 `tasks/<task-id>/README.md`，按需拆出 `validation.md` 等材料 |

以上路径相对于本 Agent Wiki 目录。这些形式不是每个任务必填的模板。若已有任务系统维护负责人、完成状态和下一步，任务文件只补充必要的调查或证据，不独立维护另一套状态。

实际验证写明日期、被测提交、环境、检查、结果、证据位置与未覆盖项；包含未提交改动时明确说明。重要外部证据要有明确的保存位置，单独留下本机临时路径不等于已长期保存。大型日志和临时产物不直接堆入文档。

### 收尾与归档

1. 确认仍然有效的设计与验证要求已进入当前来源；尚需推进的问题留在活跃任务或当前限制说明中。影响能力判断的通过、失败、阻塞与未覆盖项须能从 [证据入口](sources/validation/evidence-map.md) 定位，归档不能让当前限制随报告一起消失。
2. 保留本次实际结果、版本、环境和未覆盖项。归档表示这一轮工作或记录已收尾，不表示所有场景均已通过。
3. 将已有任务文件或目录移到 `tasks/finished_archived/`，修复外部引用与内部相对链接，并随文档改动提交到 Git。

归档保留当时的判断与证据，不随新实现改写成当前结论。已有单份验收报告可以按原文件名直接归档，不必补建任务目录或 README，也不把整份执行报告搬进 `sources/validation/`。

## 检索边界

普通开发优先读取当前来源、短页面和相关代码，活跃任务只按本次工作需要选读；任务目录位于 Agent Wiki 内也不意味着要批量加载。Wiki 索引与短页面不持续追加历史报告清单。

仓库根目录的 `.ignore` 将 `docs/agent-wiki/tasks/finished_archived/` 和 `docs/releases/` 排除出从仓库根目录进行的默认递归 `rg` 与 `rg --files`。这些文件继续由 Git 跟踪，不加入 `.gitignore`。发布说明是具体版本的变更与交付记录，不作为当前功能规范；发布流水线按指定路径读取它们。

判断功能是否已经验收时，先从 [证据入口](sources/validation/evidence-map.md) 定位并读取对应报告；未收录不等于未通过。编写发布说明、比较版本、追溯回归，或当前资料不足以解释具体问题时，也可定向读取必要的历史材料。从仓库根目录运行：

```sh
# 当前工程知识。
rg -n -- '关键词' docs/agent-wiki/sources docs/agent-wiki/wiki

# 追溯具体任务的历史证据。
rg --no-ignore -n -- '关键词' docs/agent-wiki/tasks/finished_archived

# 编写发布说明或比较具体版本。
rg --no-ignore -n -- '关键词' docs/releases
```

当前文档和发布说明可以保留必要的历史证据链接；沿链接读取前明确要追溯的问题，核对记录版本与当前实现，不递归展开所有引用，也不把旧版本通过结果当作本次验证。

`.ignore` 是默认检索规则，不是访问权限。直接读取、向 `rg` 显式指定被排除的目录或文件、其他搜索工具及覆盖过滤的参数仍可访问历史；全文索引需要单独排除历史归档与发布说明。

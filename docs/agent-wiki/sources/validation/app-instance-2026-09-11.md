## App 副本矩阵

[verify-app-instance.py](../../../../scripts/verify-app-instance.py) 已接入 [verify-release.py](../../../../scripts/verify-release.py)。测试复制两份真实 App 外壳，通过 NSWorkspace 发送启动、URL、reopen 和退出事件，使用独立的包标识与数据目录，不注册测试邀请处理器。

- 两个不同路径的 App 副本共五个并发启动，最终只保留一个 App；首页请求由留下的进程处理。
- 符号链接数据路径与真实路径收敛到相同外壳；显式独立数据目录保持独立 App/Core。
- 两批共三个邀请在 helper 忙时转交，全部由原 App 处理，内容和数量一致。
- 使用相同请求 ID 再次请求确认，不重复处理邀请；不支持的 URL 和超限批次被拒绝。
- 暂停主 App 后启动第二份，第二份不启动服务或停止 Core；恢复主 App 后完成转交，重试不重复打开首页。
- Finder 风格重新打开已有 App，复用同一进程并再次处理首页请求。
- 第二份外壳退出时不进入活动协作的退出确认/停止流程；实际 Core PID 保持不变。
- 精确终止测试主外壳后，另一个副本能重新取得锁，继续复用原 Core，测试数据保留。
- 对主外壳发送明确退出事件，仍能正常停止它所管理的 Core。

邀请由 fixture helper 拦截为测试内容；状态、启动和停止委托给包内真实 Core。测试模拟非零活动数量检查重复外壳退出路径，没有启动真实 Codex 协作，也没有发送模型输入。测试不打开浏览器，不证明真实邀请加入、窗口视觉、系统授权弹窗或跨设备 LAN；这些边界仍按各自验证契约执行。

## 本机应用与收尾

经用户授权，先备份原安装 App 与命令链接目标，再将已验证的新外壳装入 `/Applications/Team Cross.app`。内置 `0.1.1` CLI 的 SHA-256 保持不变，App 带本地修复标记并重新完成 ad-hoc 签名验证；手工遗留的 `/opt/homebrew/bin/teamcross` 链接改指向安装 App 的 helper，入口冲突消失。

只结束核对过的旧菜单栏外壳，未通过 App 的停止服务流程操作。替换前后 Core 的 PID、实例身份、数据目录和协作会话 ID 保持一致；当前 Core 继续运行原 `0.1.1-dev`，安装修复不强制切换活动协作的运行版本。原安装包和本机操作记录保留在本地忽略的 `.local-backups`，不纳入发布产物。

临时 App、Core、挂载镜像和测试辅助进程按测试路径/PID 清理；用户原生会话及代码保留。旧版外壳不实现新协调协议，升级迁移时须退出旧外壳；本轮没有增加按应用名称终止旧版本的产品行为。

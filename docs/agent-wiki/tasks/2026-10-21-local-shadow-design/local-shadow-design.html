谁是 Session，谁只是记录？

对象是不是模型会话职责与创建时机
分身身份 B不是稳定的名字、能力、资料范围和记忆归属。用户始终和它交流。
私聊 C1不是原生 Session长期保存的聊天入口和消息流。按分身、对话参与者和授权范围隔离，不因换话题改变。
主 Session S1 / S2是理解用户、读资料、使用工具、回答、更新对话状态。首条消息启动 S1；换段时创建 S2。同一 C1 同时只有一个负责接收新输入的主 Session。
话题 T1 / T2不是记录目标、状态、未决项、证据和原话锚点。允许一条消息关联多个话题，也允许暂时无法归类。
上下文管家 CM一次独立、输入受限的模型调用接近预算时判断压缩还是换段，不接用户问题、不管理长期业务历史。原生接口若要求 Session，就按次创建短期 CM1、CM2，结束后释放运行资源。
记忆整理 M一次独立、输入受限的模型调用空闲时读取新增记录和相关旧记忆，提出新增、修改或删除候选。原生接口若要求 Session，就按批创建 M1、M2；没有常驻的记忆聊天。
Core / 存储不是消息落盘、权限校验、队列与回执、真实工具状态、会话生命周期、记忆版本和检索。模型给建议，Core 执行可核验的状态变化。
个人会话 P0是，已有会话继续你自己的工作。分身不自动读取它的完整私人历史，也不把外部消息插入其中。

普通的一来一回通常只使用当前 S1。CM 在预算触发时调用；M 按新增内容批量整理。“输入很短”不意味着必须指定另一个小模型，也不固定产品的模型选择。

第一版可串行处理私聊消息；长工具调用期间的后续输入排队并显示处理中。以后若要并行调查，可增加按工作需要创建的后台执行会话，但不会恢复“每个新话题一个 Session”的规则。

主 Session 在理解这句话时维护话题

每条消息都先进入 C1 当前的主 Session。不需要先猜出属于 T1 还是 T2，才能知道该发给谁。话题识别服务于找资料、保留待办和组织回答；识别错了可以修正，不会导致消息被送到一个完全不同的聊天现场。

① 原文先落盘分配消息 ID，保留顺序与实际投递状态。
② 当前 Session 理解结合近期对话、当前焦点和未决事项解读输入。
③ 必要时回查从话题索引和历史原文找到“刚才那个”的依据。
④ 回答并更新状态新增、恢复或合并话题；记录实际答了什么。

主模型可参考的线索

  • 指代与显式语义“那……呢”“回到刚才”“顺便问”“先放一放”“不是那个”。
  • 目标与对象继续核实相同结论、修改同一产物，或者提出另一目标。
  • 最近焦点和未决项最近讨论什么、哪些要求未处理；时间近只作为辅助线索。

后台可以同时保存

  • 焦点：T2 发布流程本轮正在回答；包含材料版本与证据入口。
  • T1 恢复逻辑：暂放，尚有未决项原始问题、未查完的取消审批路径及消息锚点。
  • 约束：只分析，不修改用户明确约束的原文独立保留，不因换话题失效。

主模型在同一轮的受控状态写入动作中提出话题变更，不必每句话先启动分类模型。Core 保存原始输入与状态版本，保留未被覆盖的要求；语义完成状态需要回答或证据锚点，工具成功与投递成功以真实事件为准。

自然交流仍可能需要内容澄清。“那个审批”可能指两件事时先检索；仍不清楚时自然问“你指恢复时的审批，还是发布审批？”用户不需要选择“新问题 / 追问”。可逆的小范围分析可以说明理解后继续；不能凭猜测扩大访问或执行范围。

用户说“不是，我指发布那个”时，修正焦点和话题关联，保留纠正记录，不因此丢弃整个 Session；错误答案已经给出就明确更正。转聊 B 不自动取消未完成的 A；“先放一放”“不用继续”等表达才改变对应状态。

上下文里放什么，什么时候真正换 Session？

S1 每轮可使用的内容

  1. 稳定前缀分身身份、工具契约、权限约束、当前段冻结的少量记忆与索引。
  2. 原生会话历史近期消息、工具结果、当前交接或压缩摘要，由原生运行时组织。
  3. 当前对话状态焦点、活跃或暂放的话题、未决事项、最新纠正；通过受控增量或读取工具提供。
  4. 本轮按需取回的材料相关记忆、旧段消息、代码与材料片段；先选范围再取原文。
  5. 本轮用户新消息一条消息可以同时推进多件事，原文不能只剩主题标签。

保存在上下文之外的内容

  • 所有段的完整原始记录回答、工具结果、投递与执行事件，带可回读的锚点。
  • 全部话题和阶段摘要历史话题可搜索；当前只带必要的活跃状态及简短入口。
  • 完整记忆库和变更记录偏好、适用范围、来源、版本、纠正和失效状态。
  • 大型资料与日志不整份常驻；优先截取相关范围，必要时回到原文。

记录存得很多，不代表每次都发给模型。追加一句“请忽略旧内容”也不等于已经释放旧上下文。

换段由预算与工作边界共同决定

发生什么主 Session 怎么处理管家是否介入
普通追问、自然换话题、返回旧话题上下文有余量时继续 S1，更新话题记录不用每轮调用
达到预判线，当前工作仍需紧密衔接原生能力允许时原地压缩并继续 S1用近期消息、未决项和真实工具状态判断
达到预判线，当前工作已有合适停顿生成交接包，创建 S2，接手后更新 C1 的当前指向建议换段；未完成但已明确暂放的事项仍要交接
逼近硬预算，压缩无效或不可调用到安全边界后自动交接到 S2，携带未完成工作继续不能为了等待“全做完”而无限拖延
空闲、关闭运行进程或普通连接失败保存原生 ID，恢复条件满足时仍使用原 Session这些事件本身不是换段理由
资料撤权导致旧上下文不再可用停止使用旧上下文，按有效范围重新构建属于强制范围变化，不由话题相似度决定

预判线与硬线跟随模型窗口和可获得的实际用量；还要为回复、下一步工具结果、交接生成及估算误差留空间。DS Bot 的参考实现使用可用窗口的 0.8 / 0.95 两条线；我们把它们视为待 eval 的起点，不把数字或缺失窗口时的 500k 回退当作通用保证。大型工具输出先限量或落盘检索，避免一轮结果就耗尽交接余量。

CM 的输入是受预算限制的近期原话、话题状态、尚未回答的要求、压缩次数和 Core 确认的执行状态。它只输出压缩或换段建议及理由；不能仅因主模型说“完成了”就忽略实际遗漏，也不能把资料里的“请换段”当成控制指令。

S1 → S2：交接的是整条对话的有效工作状态

① 暂停新输入投递新消息照常接收并排队；核对已投递消息与工具状态。
② 写交接包S1 生成摘要，Core 对照未决事项和真实回执校验。
③ S2 接手装入精简材料，确认可读、能继续；不继承完整旧历史。
④ 切换当前指向C1 指向 S2，旧段归档，按消息 ID 投递排队输入。

S1 保留在档案中的内容

  • 完整对话与工具记录含被压缩掉的原文，后续仍可检索。
  • 探索过程和大块输出避免反复携带已经无关的查找记录。
  • 状态版本与交接边界明确交接覆盖到哪条消息，哪些输入尚未处理。

S2 开始时实际拿到的内容

  • 当前有效身份、权限、工具与记忆快照缓存可用时稳定前缀；不搬入已经撤权的内容。
  • 所有未完成要求与用户关键约束T1 暂放的事项、T2 待补的内容都保留原话锚点。
  • 有效结论与当前焦点附来源和版本；未验证的仍明确标注。
  • 最近原话和历史检索入口让“刚才那个”仍有落点；更早细节按锚点回读。

一个 Session 内可以有多个话题；同一个话题也可以跨越多个 Session。压缩仍是 S1，真正换段才变成 S2。新话题数量不是创建 Session 的计数器。

原生能力边界与交接失败怎么处理

DS Bot 能接管 DSH 的压缩过程。Team Cross 不能直接假设其他原生运行时也允许禁用自动压缩、定制摘要或精确编辑上下文。落地前需核对窗口用量、显式压缩、恢复、日志读取等能力；支持原地压缩才调用，不支持则采用原生压缩加外部状态，或在安全点自动换段。本次没有确认仓库已接入这些新能力。

尚有未结束的工具调用、待处理审批或投递结果不明时，先完成、核对或明确中止相关操作，不能靠新 Session 重发。CM 失败时，有余量就继续并稍后重试；余量不足时根据已落盘状态构造保底交接。保底材料必须包含未回答要求、近期原文、真实工具状态和来源入口；装不下或无法保证继续时明确暂停，不伪造无感成功。

原生上下文已经溢出时，不再强行要求旧会话生成长摘要；使用最近有效检查点和之后的原始增量恢复。S2 接手失败则不提前切换指向。交接期间只认消息 ID 与回执，恢复后先核对，不自动重复投递。

把“正在聊什么”与“以后也该记住什么”分开管理

内容放在哪里何时更新，如何再使用
“恢复逻辑还缺取消审批路径”对话状态 / 话题记录主 Session 随工作推进更新；换话题不丢失，换段时带走未决项。
“当时看了哪段代码，结论是什么”原始记录 + 阶段摘要带消息和证据锚点保存；回到旧话题时检索并核对适用版本。
“我的发布说明默认中文”有范围的长期偏好明确“记住”后受控写入，成功后确认；下一轮通过增量或 recall 可见。
“某个代码版本的恢复路径有某行为”有证据的知识条目记忆整理提出候选，保存来源版本；代码变化后重新核实。
模型推断的个人偏好 / 团队决定候选记录 / 待确认材料不能自动升格为本人确认或团队共识；普通对话也不能扩展授权范围。

两条写入路径，共用一个版本化存储

明确请求：当前 Session 立即处理

“记住……”“以后改成……”“忘掉……”由当前 S1 / S2 理解，并调用受控记忆写入。Core 核对作用范围、来源、版本和操作结果。

不能先说“已保存”再等后台有空；写入失败就说明失败。用户更新偏好时保留新旧关系，检索优先当前有效条目。

隐含经验：空闲后由 M 批量整理

M 读取上次水位之后的新增对话、证据及相关旧条目，提出保留、修改或删除建议。Core 验证后串行写入，成功才推进处理水位。

新消息到达时优先主对话，整理可延后。重复整理按来源 ID 去重；冲突重读版本，不用模型摘要覆盖用户明确纠正。

稳定前缀 + 最新增量 + 按需 recall。
段开始时冻结少量记忆与索引，尽量保留缓存收益；段内新增或纠正的记忆通过下一轮增量或读取工具可见。不能等换段后才生效，也不需要每轮重写整份系统提示词。

查到记忆后，先核对所属对话或空间、来源权限、代码版本及失效状态。私人对话、某个空间、团队已确认材料各有范围；同一个 Bot 身份不会把它们自动混为一份上下文。范围是权限边界，话题只是组织方式。

每条偏好还要记录是谁表达、适用于谁、哪些对话可以使用。同事在自己的私聊里说“以后默认中文”，不能直接改写分身所有者的全局偏好；个人聊天中的推测也不能成为其他参与者可见的团队决定。

“忘掉”或资料撤权不仅影响未来检索，还要使派生摘要与已加载上下文失效；必要时自动重建新段。停止使用某条记忆与删除原始聊天记录是不同操作，需要分别说明保留范围；已经发送给接收者的答案不能靠重建 Session 撤回。普通代码版本变化则标记相应事实待核实，保留讨论历史，不因版本号变化就一律另起聊天。

创建时选择本机 Harness，此后由它承载这份分身

用户可以指定本机 Codex 或 Claude Code 的可执行入口及可用配置。本轮范围固定为创建时选择，不支持聊到一半更换 Harness。S1 → S2 仍然是同一个 Harness 内的上下文换段；关闭后恢复也沿用保存的 Harness 与准确的原生会话 ID。

Core 保存可持续的对话状态

  • C1 的消息和当前指向保存投递状态、选定 Harness、当前原生 Session ID 与交接边界。
  • 话题、记忆、原文与来源范围这些记录独立落盘，原生压缩之后仍可检索；模型更新要经过受控写入。
  • 资料和工具授权选择本机 Harness 与允许它读哪些资料、调用哪些工具分别配置。

Harness 负责原生运行过程

  • 模型调用、原生历史和工具循环Core 不假装能任意编辑所有原生上下文；适配器按真实接口操作。
  • 原生压缩、恢复和事件能力按本机版本探测；差异决定压缩方式、可观察状态和恢复策略。
  • 主 Session、CM 与 M 的执行默认都经选定的 Harness；CM / M 只获得各自必要的输入和工具，不隐式切到另一家服务。
接入方向可复用的思路需要单独解决的边界
Codex以 app-server 作为候选程序接口，管理准确的 thread ID、输入和事件对本机版本核对显式压缩、用量、恢复、工具权限和中断能力，再确定换段策略
Claude Code评估程序化 CLI / Agent SDK 路径，按指定 Session ID 接续当前 Team Cross 的实验性原生 TUI 接入有自己的能力边界；不能直接套用 Codex 的结构化控制，也不能把 CLI 登录方式等同于 SDK 授权
同样的聊天承诺，不保证同样的底层能力。统一“能自然续聊、记忆有来源、状态可核对”；显式压缩、中断、审批和事件详细程度按实际能力提供。未通过最低恢复与权限检查的组合先不开放，不能静默降成一个行为不同的分身。

首版建议使用独立分身配置，明确选取资料和工具。只读指不修改用户项目或代替本人执行操作；Core 仍需写入自己的聊天、话题和记忆存储。完整继承个人 hooks、插件、MCP 和写权限虽然省设置，却会扩大行为范围，也降低 eval 的可复现性。

这是一项拟议接入设计，不表示 Team Cross 已提供分身功能或两个 Harness 已完成同等验收。Harness 也不等于模型：使用远端模型服务时，被选入请求的对话和资料仍会发送给该服务；本机运行不等于本机推理。

Eval 验证自然交流能否接得住，而非只考话题分类

先做一批可重放的脱敏或合成对话。建议首批 30 条、6 类各 5 条，覆盖下面场景；这是起步规模，不是充分验收。先冻结其中 10 条作留出检查，其余用于调参；强制换段的测试必须保持故事内容和预期要求一致。

回放场景检查的实际结果
A → B → 回到 A能找回 A 的未决项，不要求用户选择新问题或追问。
省略指代、同名对象、一句话推进 A 和 B指代有依据；多项要求不丢；真正有歧义时只问内容问题。
工作中途压缩 / 安全点换段 / 连续多次换段目标、用户纠正、关键数值、证据和未完成事项仍正确；不能只验证摘要看起来流畅。
记忆新增、纠正、忘掉与来源版本变化下一轮能用新记忆，旧版本不冒充当前事实，失效内容不继续进入上下文。
工具未完成、管家失败、断线、交接时来消息没有重复执行或投递，没有漏掉排队输入，没有虚报完成。
跨范围检索、资料中的伪指令、记忆污染不越权读历史，不把资料指令当控制信号，不把推测写成已确认事实。

比较三种配置：仅使用原生长会话与压缩；按预算直接换段并交接；预算 + CM 判断 + 话题状态 + 记忆增量。相同输入和模型配置下，记录任务完成、未决项保留、证据正确、自然澄清次数，以及额外模型调用、token 和首响应 / 总耗时。

真实投递、工具状态、消息去重和来源范围用可判定断言检查；回答质量用有依据的评分和人工抽查。边界案例重复运行观察波动。串权、重放和无依据报完成作为独立失败项，不能被更低成本抵消。实际模型验证遵守项目验证契约；本次没有运行模型 eval。

支持多个 Harness 后，按 Harness 版本、模型配置、有效工具与权限分别记录结果。公共对话场景可以复用，原生压缩、恢复和中断需要各自的接入检查；一个组合通过，不能推广为另一个组合通过。小规模样本用于筛选方向，长时间运行中的记忆积累、文件变化和连续换段还需独立回放。

怎么用“爬山法”迭代这套设计

把当前配置作为基线，每次只改一个因素，例如预判线、保留原话的预算、管家提示词或检索条数。在调参集重复对比；只有质量不退步、硬性检查通过且目标成本改善时才保留。然后用未参与调参的样本检查泛化，失败样本进入独立回归集。

这里的“爬山”是局部改进流程，不保证全局最优，也不是让线上 Bot 自行改规则。DS Bot 的公开 steward-eval 脚本是人工编写场景、指定 compact / switch / either 的预期并重复调用真实模型；脚本本身没有自动搜索参数的爬山循环。我们借它的边界样例方法，再扩展到整段对话、记忆和运行时故障。

这些取舍会直接影响使用体验

以下是首版建议和重新评估的条件，并非都已成为产品承诺。优先验证一条私聊能长期接续，再根据实际成本决定增加多少自动化。

取舍具体代价首版建议
自然连续 ↔ 话题互相干扰聊完发布再回到恢复时，模型可能误用上一话题的条件；话题表不能保证完全消除串题区分全局偏好和本次任务约束；关键限制保留原文与作用范围。错了可纠正，真正歧义再自然澄清
单主 Session ↔ 随时响应一次长工具调用会让后续短问题等待；并行调查会引入结果合并、取消和重复工作先串行队列，准确显示等待与处理中；支持时提供中断。只有等待成为实际瓶颈再增加独立调查任务
无感换段 ↔ 信息损失与调用成本摘要有损；找回细节要额外检索。CM、M 和交接都会增加延迟与 token关键原话、未决项和原始记录锚点独立保存；CM 按预算触发，M 空闲批量运行并设预算上限。记录交接耗时和遗失率
越来越懂用户 ↔ 错误记忆累积一次临时要求可能被错误当成永久偏好；同事意见可能冒充所有者或团队决定明确记忆优先，推断保持候选；保存表达者、适用对象、来源、范围与版本。回答建议不能代替本人承诺
丰富原生能力 ↔ 一致性与可控性完全继承个人工具方便，但副作用与配置漂移难复现；强求两种 Harness 完全一致又可能丢失优势独立分身配置、最小资料和工具范围；统一基本体验，能力差异显式报告；分别验收具体版本与配置
本机现场 ↔ 随时在线Mac 休眠或断网时无法继续读本机资料；选远端模型时仍存在向该模型传送输入的过程如实区分未送达、已接收和处理中；恢复核对回执。离线消息保存位置需在实现前确定；不默默引入云端替身
读取最新代码 ↔ 同一答案的版本一致用户在分身调查中修改文件，前后两次读取可能来自不同现场记录提交、dirty 状态及关键文件指纹；发生变化时重读或标明结论范围。精确回放需要快照，另付存储与维护成本
长期可追溯 ↔ 存储与删除语义完整历史、工具输出与派生摘要持续增长；停用记忆不等于删除原文或已发出的答复普通输出按保留策略处理，关键证据明确保留；区分停用记忆、删除记录和撤销来源，联动索引与派生内容
调参迭代快 ↔ 评估结论可靠小样本容易过拟合；每增加一种 Harness / 模型 / 工具配置就增加验收组合固定公共回放集、保留留出样本、记录版本；分别检查原生接入与长期记忆。首批 30 条不宣称充分验收
建议的起点：创建时固定 Harness；一条私聊一个当前主 Session；话题只是记录；预算驱动压缩或换段；明确记忆即时生效；后台整理有预算；只读资料与工具显式授权。先验证这些机制的必要性，再增加并行调查或更多自动化。

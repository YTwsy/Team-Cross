谁是 Session，谁只是记录？

同一空间与同一分身共用 C1。B 提问、C 补充时，双方与其他空间成员都能阅读这条对话，输入由 Core 排序后进入当前主 Session。消息保留实际作者，个人偏好不会自动成为团队规则；不同空间分别维护上下文。

对象是不是模型会话职责与创建时机
分身身份 B不是稳定的名字、能力、资料范围和记忆归属。用户始终和它交流。
空间共享对话 C1不是原生 Session同一空间与同一分身的长期消息流，空间成员可阅读和参与；保存作者、顺序与当前主 Session，不按成员拆成私人上下文。
主 Session S1 / S2是理解用户、快速回答、派发调查、汇总结果和更新对话状态。首条消息启动 S1，换段时创建 S2。同一 C1 只有一个主 Session 接用户新输入，但不必等待所有后台任务完成才进入下一轮。
工作上下文 W1 / W2子 Agent 独立上下文，或独立原生 Session收到明确的长任务时创建，承担调查并保存工具过程；不是第二个用户聊天窗口。后台运行，按任务完成或取消；不与话题一一对应。
任务 J1 / J2不是Core 保存的任务记录，关联 C1、原始消息、任务版本、W1、真实状态与结果。即使 S1 换成 S2，J1 仍存在。
话题 T1 / T2不是记录目标、状态、未决项、证据和原话锚点。允许一条消息关联多个话题，也允许暂时无法归类。
上下文管家 CM一次独立、输入受限的模型调用接近预算时建议原生压缩或换段，由 Core 校验并协调执行；不接用户问题、不替换原生摘要算法。原生接口若要求 Session，就按次创建短期 CM1、CM2，结束后释放运行资源。
记忆整理 M一次独立、输入受限的模型调用空闲时读取新增记录和相关旧记忆，提出新增、修改或删除候选。原生接口若要求 Session，就按批创建 M1、M2；没有常驻的记忆聊天。
Core / 存储不是消息落盘、自有资源的范围校验、任务与结果事件、回执、真实工具状态、会话生命周期、记忆版本和检索。沿用原生权限，不把继承的全部工具包装成强制只读。
个人会话 P0是，已有会话继续你自己的工作。分身不自动读取它的完整私人历史，也不把外部消息插入其中。

普通的一来一回通常只使用当前 S1。CM 在预算触发时调用；M 按新增内容批量整理。“输入很短”不意味着必须指定另一个小模型，也不固定产品的模型选择。

首版即区分前台对话与后台长任务。主会话一轮生成时仍可能短暂忙碌；新消息按原生能力补充、中断或短暂排队，但不因 W1 还在调查而一直等到它完成。

主 Agent 继续聊，后台 Agent 把长任务做完

单主 Session 是一个对话入口，不是一个串行执行槽。长调查交给 W1；主 Agent 派发后结束当前轮，下一条用户消息仍进入 S1。短问题直接回答，不必每句话都创建子 Agent。

前台：S1 → S2

  • 理解、回应与协调回答短问题，说明真实进度，接收新的要求或取消请求。
  • 上下文保持简洁近期对话、话题与约束、J1 的版本和进度、必要结果摘要。
  • 统一向用户答复核对后台结果是否仍符合当前要求，必要时回读证据。

后台：W1 / W2

  • 只承担明确的一项工作获得目标、相关原话、约束、代码版本与证据入口；工具配置依原生规则继承。
  • 保留自己的探索上下文长日志与大量代码阅读留在工作上下文中，不持续灌入主会话。
  • 完成后保存结果并发事件带任务 ID、版本、结果状态和来源；由 Core 投递给 C1 当时的主 Session。
用户仍在同一个窗口交流后台发生什么
“深入查一下 epoch 和取消审批的恢复路径。”S1 创建 J1，交给 W1。派发成功后说明正在调查，结束当前轮，不同步等待全部结果。
“调查时顺便解释一下发布回滚需要哪些步骤。”S1 正常回答另一问题；W1 继续调查。必要时另一项长工作另建 W2。
“刚才的调查先只看取消审批，其他分支不用了。”J1 更新为 v2；向可接收补充的 W1 传达变化。旧 v1 结果晚到时只作参考，不冒充 v2 的完成答复。
主会话接近预算，用户继续自然交流。S1 → S2 交接话题与 J1 索引。J1 属于 C1，后台结果按 C1 找当前主会话；不把运行中的原生子 Agent 假装搬到 S2。
“刚才查得怎么样了？”已完成就由当前主 Agent 整理有证据的答复；未完成就给真实进度。重复完成事件不重复发送。

任务记录至少保存原始消息、任务版本、工作上下文 ID、状态与结果水位。“请求停止”与“确实停止”分开记录；不清楚运行状态时先核对，不自动重跑。主会话换段时携带任务索引，工作上下文自己的预算与检查点独立管理。

原生子 Agent 与独立工作 Session 怎样选择？

优先使用可观测、可恢复的原生后台子 Agent，验证它能否跨主轮结束继续工作，以及主会话换段后如何保留执行端和接收结果。若原生生命周期不满足，就从任务创建时使用同一 Harness 的独立工作 Session，由 Core 管理；不要求用户选择。

存在 spawn 工具不等于前台一定可响应：主 Agent 若同步等结果，仍会阻塞。实现必须把派发、下一轮输入和结果事件分开调度。前台优先，限制后台并发；共享速率限制、当前一轮生成与原生权限等待仍可能带来延迟，不能承诺零等待。

工作 Agent 沿用原生继承规则；原生角色自身的模型、工具和权限限制仍有效，Team Cross 不额外裁剪，也不绕过这些限制。这里只讨论拟议架构，不表示两个 Harness 的接入路径已经完成验收。

主 Session 在理解这句话时维护话题

每条消息都先进入 C1 当前的主 Session。不需要先猜出属于 T1 还是 T2，才能知道该发给谁。话题识别服务于找资料、保留待办和组织回答；识别错了可以修正，不会导致消息被送到一个完全不同的聊天现场。

① 原文先落盘分配消息 ID，保留顺序与实际投递状态。
② 当前 Session 理解结合近期对话、当前焦点和未决事项解读输入。
③ 必要时回查从话题索引和历史原文找到“刚才那个”的依据。
④ 回答并更新状态新增、恢复或合并话题；记录实际答了什么。

主模型可参考的线索

  • 指代与显式语义“那……呢”“回到刚才”“顺便问”“先放一放”“不是那个”。
  • 目标与对象继续核实相同结论、修改同一产物，或者提出另一目标。
  • 最近焦点和未决项最近讨论什么、哪些要求未处理；时间近只作为辅助线索。

后台可以同时保存

  • 焦点：T2 发布流程本轮正在回答；包含材料版本与证据入口。
  • T1 恢复逻辑：暂放，尚有未决项原始问题、未查完的取消审批路径及消息锚点。
  • 约束：只分析，不修改用户明确约束的原文独立保留，不因换话题失效。

主模型在同一轮的受控状态写入动作中提出话题变更，不必每句话先启动分类模型。Core 保存原始输入与状态版本，保留未被覆盖的要求；语义完成状态需要回答或证据锚点，工具成功与投递成功以真实事件为准。

自然交流仍可能需要内容澄清。“那个审批”可能指两件事时先检索；仍不清楚时自然问“你指恢复时的审批，还是发布审批？”用户不需要选择“新问题 / 追问”。可逆的小范围分析可以说明理解后继续；不能凭猜测扩大访问或执行范围。

用户说“不是，我指发布那个”时，修正焦点和话题关联，保留纠正记录，不因此丢弃整个 Session；错误答案已经给出就明确更正。转聊 B 不自动取消未完成的 A；“先放一放”“不用继续”等表达才改变对应状态。

送达和手动重发

分身所在 Mac 的 Core 持久接收后才显示“已送达”，不代表模型已经回答。发送失败保留内容并显示“重发”按钮；不增加云端信箱、定时重试或联网后自动发送。

重发复用原消息 ID 与内容，接收端返回已有接收状态，不重复启动模型或后台任务。回执丢失也按同一 ID 核对；若原生投递结果不明，先查状态，不直接再执行。用户编辑内容后发送属于新消息。

上下文里放什么，什么时候真正换 Session？

S1 每轮可使用的内容

  1. 稳定前缀分身身份、工具契约、原生有效权限、当前段冻结的少量记忆与索引。
  2. 原生会话历史近期消息、短工具结果、当前交接或压缩摘要，由原生运行时组织。
  3. 当前对话与任务状态焦点、活跃话题、未决事项、纠正，以及 J1 / J2 的版本、状态和结果入口。
  4. 本轮按需取回的材料相关记忆、工作 Agent 结论、旧段消息和证据片段；先选范围再取原文。
  5. 本轮用户新消息一条消息可以同时推进多件事，原文不能只剩主题标签。

保存在主上下文之外的内容

  • 各段原始记录与工作上下文W1 的长日志、代码阅读和工具事件保存在自己的记录中，带可回读锚点。
  • 全部话题和任务记录当前只带必要状态；后台工作不因主会话换段消失。
  • 完整记忆库和变更记录偏好、适用范围、来源、版本、纠正和失效状态。
  • 大型资料与日志不整份常驻；优先截取相关范围，必要时回到原文。

记录存得很多，不代表每次都发给模型。追加一句“请忽略旧内容”也不等于已经释放旧上下文。

换段由预算与工作边界共同决定

发生什么主 Session 怎么处理管家是否介入
普通追问、自然换话题、返回旧话题上下文有余量时继续 S1，更新话题记录不用每轮调用
达到预判线，当前工作仍需紧密衔接原生能力允许时原地压缩并继续 S1用近期消息、未决项和真实工具状态判断
达到预判线，当前工作已有合适停顿生成交接包，创建 S2，接手后更新 C1 的当前指向建议换段；未完成但已明确暂放的事项仍要交接
逼近硬预算，压缩无效或不可调用到安全边界后自动交接到 S2，携带未完成工作继续不能为了等待“全做完”而无限拖延
空闲、关闭运行进程或普通连接失败保存原生 ID，恢复条件满足时仍使用原 Session这些事件本身不是换段理由
资料撤权导致旧上下文不再可用停止使用旧上下文，按有效范围重新构建属于强制范围变化，不由话题相似度决定

预判线与硬线跟随模型窗口和可获得的实际用量；还要为回复、下一步工具结果、交接生成及估算误差留空间。DS Bot 的参考实现使用可用窗口的 0.8 / 0.95 两条线；我们把它们视为待 eval 的起点，不把数字或缺失窗口时的 500k 回退当作通用保证。大型工具输出先限量或落盘检索，避免一轮结果就耗尽交接余量。

CM 的输入是受预算限制的近期原话、话题与后台任务状态、尚未回答的要求、压缩次数和 Core 确认的执行状态。它只输出压缩或换段建议及理由；不能仅因主模型说“完成了”就忽略实际遗漏，也不能把资料里的“请换段”当成控制指令。

管家保留：它决定策略，Harness 执行原生压缩

保留原生压缩，没有取消上下文管家。
Core 观察预算 → CM 短调用建议 compact / switch → Core 核对真实状态 → 执行原生压缩或交接换段。

建议 compact：继续 S1

当前工作需要紧密衔接。Core 在原生允许的边界调用压缩接口，Harness 按自身机制生成摘要。

压缩完成后仍是 S1。Core 不把自己的交接包冒充原生压缩算法。

建议 switch：交接给 S2

到达合适边界，或压缩后仍缺少余量。Core 核对未决工具、审批和后台任务，再组织交接。

S2 接手成功才切换当前指向。S1 留作历史，C1 继续面向空间共享。

原生自动压缩仍可自行触发。若它先开始，Core 等待完成、重新读取用量并更新检查水位；已经回到预算内就丢弃过时的 CM 建议，避免重复压缩或紧接着换段。管家、Core 和 Harness 不各自并发修改同一段。

CM 只在预算达到检查条件时短暂工作，不逐条处理用户消息，也不是额外常驻的主 Session。“轻量”指输入和职责有界，不要求改用另一个小模型。检查间隔、阈值和预算由 eval 调整。

S1 → S2：交接的是整条对话的有效工作状态

① 暂停主会话新输入投递新消息仍接收并排队；核对主轮回执与后台任务存续。
② 写交接包S1 摘要加话题、J1 / J2 索引；Core 校验状态和结果水位。
③ S2 接手装入精简材料和任务入口；独立 W1 可以继续运行。
④ 切换当前指向C1 指向 S2；后续输入和后台结果投递给当前主会话。

S1 保留在档案中的内容

  • 完整对话与工具记录含被压缩掉的原文，后续仍可检索。
  • 探索过程和大块输出避免反复携带已经无关的查找记录。
  • 状态版本与交接边界明确交接覆盖到哪条消息，哪些输入尚未处理。

S2 开始时实际拿到的内容

  • 当前有效身份、权限、工具与记忆快照缓存可用时稳定前缀；不搬入已经撤权的内容。
  • 所有未完成要求与用户关键约束T1 暂放的事项、T2 待补的内容都保留原话锚点。
  • 有效结论与当前焦点附来源和版本；未验证的仍明确标注。
  • 最近原话和历史检索入口让“刚才那个”仍有落点；更早细节按锚点回读。

一个主 Session 内可以有多个话题；同一个话题也可以跨越多段。压缩仍是 S1，真正换段才变成 S2。后台任务属于 C1，其原生执行端的存续和结果回传要单独验证；不会因为新建 S2 就假定它自动迁移。新话题数量不是创建 Session 的计数器。

原生能力边界与交接失败怎么处理

DS Bot 能接管 DSH 的压缩过程。我们首版保留 Codex 原生自动压缩及摘要机制，由 CM 建议、Core 协调；不直接替换摘要或改写原生历史。落地前核对用量、显式压缩、恢复与日志读取，后续 Claude 单独适配。本次没有确认仓库已接入这些新能力。

主轮尚有未结束的同步工具、待处理审批或投递结果不明时，先完成、核对或明确中止相关操作，不能靠新 Session 重发。独立后台工作可以继续，但要保留执行端、权限等待和结果回传的准确归属；原生子 Agent 若绑定 S1，需验证父会话存续或改用独立工作 Session，不能直接销毁父执行端。CM 失败时，有余量就继续并稍后重试；余量不足时用落盘状态构造保底交接，包含未答要求、任务索引、近期原文、真实状态和来源入口。无法保证继续时明确暂停。

原生上下文已经溢出时，不再强行要求旧会话生成长摘要；使用最近有效检查点和之后的原始增量恢复。S2 接手失败则不提前切换指向。交接期间按消息及结果事件 ID 去重，恢复后先核对，不自动重复投递。

把“正在聊什么”与“以后也该记住什么”分开管理

内容放在哪里何时更新，如何再使用
“恢复逻辑还缺取消审批路径”对话状态 / 话题记录主 Session 随工作推进更新；换话题不丢失，换段时带走未决项。

两条写入路径，共用一个版本化存储

明确请求：当前 Session 立即处理

“记住……”“以后改成……”“忘掉……”由当前 S1 / S2 理解，并调用受控记忆写入。Core 核对作用范围、来源、版本和操作结果。

不能先说“已保存”再等后台有空；写入失败就说明失败。用户更新偏好时保留新旧关系，检索优先当前有效条目。

隐含经验：空闲后由 M 批量整理

M 读取上次水位之后的新增对话、证据及相关旧条目，提出保留、修改或删除建议。Core 验证后串行写入，成功才推进处理水位。

新消息到达时优先主对话，整理可延后。重复整理按来源 ID 去重；冲突重读版本，不用模型摘要覆盖用户明确纠正。

稳定前缀 + 最新增量 + 按需 recall。
段开始时冻结少量记忆与索引，尽量保留缓存收益；段内新增或纠正的记忆通过下一轮增量或读取工具可见。不能等换段后才生效，也不需要每轮重写整份系统提示词。

通过 Core 查到记忆后，核对所属对话或空间、来源权限、代码版本及失效状态。Core 管理的私人对话、空间与团队材料各有范围，不因 Bot 身份相同就自动合并。全量继承的原生自动记忆、hooks 和 MCP 按本机原有方式运行，这套范围检查不等于将它们全部隔离；也不把 P0 的完整 transcript 自动当作分身启动上下文。

每条偏好还要记录是谁表达、适用于谁、哪些对话可以使用。同事在自己的私聊里说“以后默认中文”，不能直接改写分身所有者的全局偏好；个人聊天中的推测也不能成为其他参与者可见的团队决定。

“忘掉”或资料撤权不仅影响未来检索，还要使派生摘要与已加载上下文失效；必要时自动重建新段。停止使用某条记忆与删除原始聊天记录是不同操作，需要分别说明保留范围；已经发送给接收者的答案不能靠重建 Session 撤回。普通代码版本变化则标记相应事实待核实，保留讨论历史，不因版本号变化就一律另起聊天。

创建时选择本机 Harness，此后由它承载这份分身

用户可以指定本机 Codex 或 Claude Code 的可执行入口及可用配置。本轮范围固定为创建时选择，不支持聊到一半更换 Harness。S1 → S2 仍然是同一个 Harness 内的上下文换段；关闭后恢复也沿用保存的 Harness 与准确的原生会话 ID。

Core 保存可持续的对话状态

  • C1 的消息和当前指向保存选定 Harness、主 Session ID、任务 J1 / J2、回执与交接边界。
  • 话题、记忆、原文与来源范围自有记录独立落盘，原生压缩后仍可检索；工作 Agent 结果带任务版本。
  • 有效配置的引用与指纹观察原生实际加载结果，不另建空配置或裁剪工具；凭据不写进记录和提示词。

Harness 负责原生运行过程

  • 模型调用、历史和工具循环沿用本机模型路由、认证、hooks、插件、skills、MCP、原生记忆与权限。
  • 压缩、恢复、后台工作与事件按本机实际版本和配置验证，不把不同运行时的接口当作完全等价。
  • 主 Agent、工作 Agent、CM 与 M都经选定 Harness 执行，按原生规则继承模型及角色配置；Core 不另选服务或 Token Plan。

首版确定全量继承本机有效配置。
按原生优先级加载 hooks、插件、skills、MCP、模型路由、认证、自动记忆、权限与子 Agent 设置，不额外建一套删减配置。启动、换段与恢复报告实际加载结果；配置变更后重新检查，不把旧快照当作当前环境。

默认仍帮助用户调查和分析，具体操作遵循用户指令及原生权限；这不等于强制只读沙箱，也不承诺隔离所有个人资源。继承配置不等于导入 P0 的全部历史，更不自动授权代替本人对外承诺。工作 Agent 沿用原生对子 Agent 的继承和限制，Core 只为其管理的记录校验范围。

这是一项拟议接入设计，不表示 Team Cross 已提供分身功能或两个 Harness 已完成同等验收。Harness 也不等于模型：使用远端模型服务时，被选入请求的对话和资料仍会发送给该服务；本机运行不等于本机推理。

Eval 验证自然交流能否接得住，而非只考话题分类

先做一批可重放的脱敏或合成对话。建议首批 30 条、6 类各 5 条，覆盖下面场景；这是起步规模，不是充分验收。先冻结其中 10 条作留出检查，其余用于调参；强制换段的测试必须保持故事内容和预期要求一致。

回放场景检查的实际结果
A → B → 回到 A能找回 A 的未决项，不要求用户选择新问题或追问。
省略指代、同名对象、一句话推进 A 和 B指代有依据；多项要求不丢；真正有歧义时只问内容问题。

记忆新增、纠正、忘掉与来源版本变化下一轮能用新记忆，旧版本不冒充当前事实，失效内容不继续进入上下文。
后台任务运行时来消息、改要求、取消、换段和故障主 Agent 能继续回应；旧版本结果不冒充新要求；重复结果不重复发送，未知状态不自动重跑。

比较三种配置：仅使用原生长会话与压缩；按预算直接换段并交接；预算 + CM 判断 + 话题状态 + 记忆增量。相同输入和模型配置下，记录任务完成、未决项保留、证据正确、自然澄清次数，以及额外模型调用、token 和首响应 / 总耗时。

真实投递、工具状态、消息去重和来源范围用可判定断言检查；回答质量用有依据的评分和人工抽查。边界案例重复运行观察波动。串权、重放和无依据报完成作为独立失败项，不能被更低成本抵消。实际模型验证遵守项目验证契约；本次没有运行模型 eval。

支持多个 Harness 后，按 Harness 版本、模型配置、有效工具与权限分别记录结果。公共对话场景可以复用，原生压缩、恢复和中断需要各自的接入检查；一个组合通过，不能推广为另一个组合通过。小规模样本用于筛选方向，长时间运行中的记忆积累、文件变化和连续换段还需独立回放。

单独验证“后台忙，前台仍能聊”。让 W1 持续运行，在此期间发送另一问题、修改任务、请求取消，并让主会话换段。分别记录接收回执、主 Agent 的实质回应与后台完成时间；快速显示“收到”不算通过。记录并发和限流、任务版本与结果事件，覆盖 W1 在交接期间完成及重复通知的情况。

全量继承后，有效配置也是实验条件。保存不含凭据的模型路由、hooks、插件、skills、MCP、权限与原生角色指纹；在实际配置上检查，不用一份人为删减的环境代表用户现场。

先以 Codex 验证本轮新增边界：空间内多人接续同一个 C1 且保留作者和偏好归属；原生自动压缩先完成时不执行过时的 CM 建议；回执丢失后手动重发同一消息只投递一次。Claude 后续独立验收。

怎么用“爬山法”迭代这套设计

把当前配置作为基线，每次只改一个因素，例如预判线、保留原话的预算、管家提示词或检索条数。在调参集重复对比；只有质量不退步、硬性检查通过且目标成本改善时才保留。然后用未参与调参的样本检查泛化，失败样本进入独立回归集。

这里的“爬山”是局部改进流程，不保证全局最优，也不是让线上 Bot 自行改规则。DS Bot 的公开 steward-eval 脚本是人工编写场景、指定 compact / switch / either 的预期并重复调用真实模型；脚本本身没有自动搜索参数的爬山循环。我们借它的边界样例方法，再扩展到整段对话、记忆和运行时故障。

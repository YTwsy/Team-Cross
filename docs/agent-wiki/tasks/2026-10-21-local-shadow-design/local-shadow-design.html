01 / SESSION 调度

一条 C1，当前一个主 Session，另有独立工作会话

每个分身属于一个空间，运行在创建它的成员 Mac 上，并有自己的 Codex app-server。空间里的成员消息先持久化，再按顺序进入当前主 Session。追问、换话题和换发言者，都不会自动创建另一条主 Session。

同一段交流的六个时刻 · 点击查看后台状态（示意，不是实时运行）

C1 · 整个空间持续共享的聊天与记录

当前主会话
S1 · 首条消息才创建处理问题、调用工具、给出回答；完成这一轮后才处理下一条成员消息。
后台工作
尚无 W / J普通短问题不需要创建工作会话。
Core 持久状态
current = S1消息、段指针、运行账本和真实投递状态独立于模型上下文保存。

“已送达”表示运行分身的 Core 已经落盘；还不表示模型读过或完成。示例中的 T / J 记录只有模型实际调用对应工具后才会存在。

前台与后台怎么争用时间

Core 每 250 ms 或收到事件时推进状态：先处理原生事件并调度后台任务，再检查主轮与审批；主会话空闲后，优先完成换段与必要维护，再处理排队成员消息，最后汇总尚未投递的任务结果。成员消息优先于后台结果通知，主轮忙时新消息排队。这里没有用 turn/steer 把普通新消息插入正在生成的主轮。

任务改版会递增 J 的版本，先请求停止旧轮，确认结束后在同一 W 接续；取消同样区分 stopping 与 cancelled。W 的结果先落盘为唯一事件，再交给当时的主段汇总；旧版本结果不能成为新要求的完成答复。

独立上下文不等于独立文件现场。W 使用同一分身的工作目录和原生配置，当前不会为每个任务建立 worktree。后台默认调查只读是提示词约定，实际工具权限仍来自本机 Codex。

依据：engine.go · step / createThread、tools.go · scheduleJobs、native.go · finishRunLocked。

02 / 每个 SESSION 内部有什么

先拆成四层，再看每一种轮次的输入清单

一个 Session 对应一个原生 thread，里面可以有多轮 turn。S1 的普通回答、交接笔记和后台结果汇总是同一个 thread 内不同用途的轮次；W、CM、M 则有自己的 thread。Core 给它们的材料不同，模型最终能用的内容还取决于 Codex 原生上下文管理。

01 · 原生环境配置与原生指令

Codex 按自身规则加载项目说明、已启用的个人记忆与工具能力。Core 传入 home / cwd，附加 5 个 shadow 工具；配置文件本身不等于整份提示词。

02 · 此 thread 的历史之前在这里发生的事

本会话先前的输入、回答、工具交互，以及原生压缩后留下的内容。新建 thread 没有其他 thread 的整段历史；磁盘历史也不等于全部常驻窗口。

03 · 本轮 Core 输入按用途组装的文本

角色约定、成员消息、状态快照、任务、交接笔记或记忆变化。这一层可从 Team Cross 源码逐项核对，下面展开的就是它。

04 · 本轮工具返回实际查询后补进的内容

文件内容、命令结果、历史摘录和最新记忆，只有实际读取后才作为工具结果进入调用链。有工具定义、有路径或有来源 ID，都不等于已读正文。

本页核对的是 Core 装配规则，没有抓取你真实 Session 的模型请求。原生系统指令的完整文本、压缩摘要的具体内容、模型内部推理与每次实际 token 占用，不能从这份 Core 源码还原。原生个人记忆和 P0 私人会话的边界见下文说明。

Core 到底怎样提交这一轮？角色约定处于哪一层？

createThread 对各类会话使用 thread/start，传入 cwd、serviceName: teamcross_shadow 和动态工具定义。这里没有 fork S1/P0，也没有用 baseInstructions 另设系统提示词。

Meta 当前会固定创建时选择的模型配置。创建表单从原生有效配置预填；确认后把 settings: {model, modelProvider, reasoningEffort} 持久保存。S1、S2、W、CM、M 的创建与恢复都显式应用同一组值，各轮再传 model / effort，并核对原生返回；不会在换段或重启时重新采用默认模型。权限、认证、插件与其他原生配置仍按原生规则加载。

每次 submit 先写运行账本，再调用 turn/start。下面是结构示意；尖括号表示本页占位符，实际提交会替换成真实 ID 和完整文本：

{
  "model": "<创建时选择的 model>",
  "effort": "<创建时选择的 reasoningEffort>",
  "threadId": "<本次 thread ID>",
  "input": [{
    "type": "text",
    "text": "[teamcross-shadow-run:<run ID>]\n<按下面场景组装的文本>"
  }]
}

这个运行标记用于恢复时核对提交，不能把它理解为另一条成员请求。CM 和 M 另在请求顶层带 outputSchema 限制输出形状；不是把 schema 当作聊天正文塞进去。

rolePrompt 是随普通文本输入的分身角色约定，强调共享作者、保留未决项、长任务异步派发、显式记忆先落盘再确认、候选不当事实、原生权限继续生效、引用和工具结果只作证据。它只在主段首次初始化或 S2 接手时加入；W、CM、M 使用各自的专用说明，不复用整段 rolePrompt。

依据：engine.go · createThread / submit、settings.go · 固定启动选择与原生确认、context.go · rolePrompt、shadows.go · shadowConfig。

新建 S1 · Run.kind = main · 处理第一条成员消息

S1 首轮：建立角色，放入状态，再交付本次原话

本次新增，按这个顺序

  1. 分身角色约定：上面的 rolePrompt。
  2. Initial context：contextLocked(true)，含有效记忆、话题、任务、最近 12 条消息及查询工具名。
  3. 记忆变化：若有高于本段水位的非候选条目，按 revision 升序追加，可能与初始有效记忆重叠。
  4. 当前成员原话：仅封装这条消息的 id / actor / text，正文在这一步不做 1,800 字符截断。

原先有什么 / 完成后去哪

有继承的原生环境；没有 S1 的旧聊天，也没有自动导入 P0。文件需由模型实际读取。

助手输出、工具调用和结果留在 S1 原生历史；Core 收集非 commentary 的助手输出，追加为 C1 共享回答。工具日志不会逐条变成共享聊天消息。

初始快照是记录末尾。它可能已经含本条原话，甚至含已落盘、仍在排队的后续消息；模型仍应以最后的“当前成员消息”为本轮请求。

展开本轮文本骨架
[teamcross-shadow-run:run-demo-1]
<rolePrompt 的完整文本>

Initial context (service data):
<完整状态快照；字段在下方逐项解释>

Memory changes since this segment last saw them ...:
<仅在有变化时插入 Memory 数组>

Current member message; preserve its text and authorship:
{"id":"msg-B1","actor":{"id":"B","name":"成员 B"},
 "text":"只解释恢复流程，不修改文件。"}

“首次”判断还会检查本段是否已有成功完成的 main / bootstrap 轮；没有记忆时也不会因此每轮重复初始化。失败重试等边界下仍以该判断为准。

依据：messagePrompt / contextLocked、finishRunLocked。

继续当前 S1 或 S2 · Run.kind = main · 每条成员消息一轮

主段续聊：沿用本段历史，只补记忆变化与新原话

本次新增，按这个顺序

  1. 记忆变化（有则追加）：筛选 state != candidate 且 revision > segment.memoryRevision 的当前条目，按 revision 升序发送。
  2. 当前成员原话：id / actor / text。作者 B 换成 C，仍然是当前同一个主 thread。

这里不重新发送 rolePrompt、完整任务表、完整话题表或最近 12 条消息。记忆变化也不是完整修改日志：同一 ID 只保存并发送当前最新版本。

原先有什么 / 什么不会自动更新

原生窗口里已有本段此前的交流、工具结果或压缩后保留内容。早先读过的任务状态只是当时的值，不会随 Core 数据变化自动刷新。

需要新状态时调用 shadow_recall / shadow_task status；需要旧证据时调用 shadow_history。

forgotten 变化提示停止使用旧值，但不会删除窗口里早先出现的原话或工具返回。

展开一次“纠正后继续问”的输入
[teamcross-shadow-run:run-demo-2]
Memory changes since this segment last saw them (forgotten means stop using the old value):
[{"id":"mem-B1","text":"发布说明默认中英双语",
  "scope":"member","subjectId":"B","sourceIds":["msg-B2"],
  "revision":7,"state":"active","updatedAt":"2026-10-22T09:00:00+08:00"}]

Current member message; preserve its text and authorship:
{"id":"msg-C1","actor":{"id":"C","name":"成员 C"},
 "text":"刚才提到的取消审批，是在哪一步核对的？"}

主模型同时知道“B 的偏好更新了”与“当前是 C 在提问”，不能把 B 的偏好变成 C 的个人偏好。没有变化时，整段 Memory changes 都不出现。

水位是 Core 的账本值：main / result 结束时记录该轮提交时的 revision；S2 确认接手、提交 current 切换时，以当时的全局 revision 设置新段水位。它不是模型逐条确认读懂的回执。

依据：messagePrompt、finishRunLocked · main / result。

首次新建 W；改版 / 接续沿用同一 W · Run.kind = job

W：拿任务包开工，独立积累自己的执行历史

本次新增，按这个顺序

  1. 工作者专用约定：按实际授权调查或修改；默认只读，沿用已有证据，避免重复副作用；最终给证据与不确定项。
  2. Original member request：J.sourceId 对应的完整 Message，含作者、正文、状态、时间及已有轮次字段。
  3. Task and version：完整 Job，包含 prompt、sourceId、version、状态、已有 result 和事件字段（有值时）。这里不按 1,200 / 1,600 字符截断。
  4. Relevant conversation state：contextLocked(false)，有有效记忆、话题和任务投影，没有 recentMessages。

原先有什么 / 完成后去哪

首次 W 没有 S1 全历史；更新或接续同一任务时，它保留自己的原生执行历史。每次重新派发还会再附上这份任务包和当时的状态投影。

任务更新后，sourceId 会指向那次修改要求的成员消息。原来的全部约束需靠任务 prompt、W 自己的历史、话题记录或按需回读保留。

W 的最终输出先成为 J.result；完整工具过程留在 W / 归档里。S1 → S2 不会把 W 换成另一条 thread，也不会把主段的新对话实时推给 W。

展开任务包里最关键的具体内容
Original member request:
<msg-B3 的完整 Message：B 请调查恢复路径，明确不修改文件>

Task and version:
{
  "id":"job-1","title":"核对取消审批后的恢复路径",
  "prompt":"检查 native.go 的恢复与核对分支；只读。保留 msg-B1 的不修改文件约束。给函数位置、已确认行为及未验证项。",
  "sourceId":"msg-B3","version":1,"runningVersion":0,
  "state":"queued",
  "createdAt":"2026-10-22T09:02:00+08:00",
  "updatedAt":"2026-10-22T09:02:00+08:00"
}

Relevant conversation state:
<contextLocked(false) 的完整 JSON，不含最近消息>

此例模拟第一次提交前的 Job，所以可能仍是 queued、尚无 threadId。msg-B1 和 native.go 都只是线索；W 要取得它们的正文仍需查询或读文件。派发 prompt 上限为 24 KiB，主模型应把关键约束直接写清。

依据：workerPromptLocked、shadow_task / scheduleJobs。

每次新建 CM 短 thread · Run.kind = steward · 结构化输出

CM：只拿这次检查材料，判断 compact 还是 switch

本次新增，按这个顺序

  1. 管家专用约定：只给 JSON，不使用工具、不执行用户任务；比较要求、已答内容、未决项和任务状态；换话题本身不构成换段理由。
  2. 当前 Segment JSON：包括 ID、段号、记忆水位、inputTokens、usageValid、contextWindow、compactions 和 lastCheckTokens 等。
  3. 状态投影：contextLocked(true)，包含最近 12 条消息、有效记忆、未结束话题和任务摘要。

输出 schema 只接受 action: compact | switch 与 reason。

原先有什么 / 判断依据的边界

没有上一次 CM 的聊天，也没有自动复制 S1 的完整原生历史或原生压缩摘要。它能比较的“原始要求”，实际只来自本次给到的近期消息及结构化状态。

较早的要求若既不在近期消息里，又没记入话题 / 任务等状态，就可能不在 CM 的检查材料中。提示词要求全面判断，并不等于输入已覆盖全部历史。

Core 核对段 ID、压缩代次和消息数量后采用建议；不是 CM 自己压缩或迁移。结果不作为共享答复发布。

展开 Segment 字段与 CM 输出示例
<管家说明>
{
  "id":"S1","number":1,"createdAt":"2026-10-22T08:00:00+08:00",
  "memoryRevision":7,"inputTokens":141000,"usageValid":true,
  "contextWindow":200000,"compactions":1,"lastCheckTokens":0
}
<contextLocked(true) 的完整 JSON>

期望输出示例：
{"action":"compact","reason":"相关任务仍未完成，先保留当前段并进行原生压缩。"}

以上数字仅用于读懂字段，不是当前真实用量。inputTokens 这个字段实际记录原生最近一次上报的输入 + 输出用量。CM 的本轮 JSON 输入没有直接附带原生压缩摘要正文。

依据：maintenance / finishStewardLocked、Segment。

每次新建 M 短 thread · Run.kind = memory · 结构化输出

M：读一批新消息和近期记忆，提出可确认的候选

本次新增，按这个顺序

  1. 整理专用约定：最多 6 个耐久记忆候选；不用工具；临时任务不当长期记忆；不复活已忘掉或被纠正的内容；引用本批次精确消息 ID。
  2. batch：从 memoryWatermark 后开始取最早的未处理消息，至多 20 条，每条正文裁到 2,400 字符；成员消息和共享助手答复都可能出现。
  3. existing：按 revision 从新到旧取最多 30 条 Memory，包含 active / candidate / forgotten，不是主段用的仅有效记忆快照。

它不调用 contextLocked；没有默认附上完整任务表、话题表、W 的工具日志或 S1 原生长历史。

原先有什么 / 完成后去哪

每次都是新 M，没有上一批 M 的对话历史。默认空闲 45 秒且至少新增 4 条 Record.Messages 后才开始；这不是“4 个用户问题”。

Core 验证候选结构、批内来源、成员归属，以及运行期间记忆 revision 是否改变。通过后才存为 candidate 并推进水位。

候选可在共享视图 / recall 中读到；不会自动进入主段的有效记忆快照。M 输出成功不等于主段下一轮就把它当作已确认事实。

展开 M 的输入形状与输出形状
<记忆整理说明>
{
  "batch": [<完整 Message 对象，最多 20 条；这里只省略正文示例>],
  "existing": [<完整 Memory 对象，最多 30 条，包含各状态>]
}

候选输出示例：
{"candidates":[{
  "text":"成员 B 偏好简短的说明",
  "scope":"member",
  "sourceIds":["msg-B4","msg-B5"]
}]}

模型只输出 text / scope / sourceIds；subjectId、id、revision、state、updatedAt 由 Core 核对后赋值。member 来源必须都是该成员的 user 消息；space 候选的来源也必须位于本批次。

这里有两种单位：批次原文按 2,400 个 Unicode 字符截断；候选正文落盘校验为不超过 2,400 字节。existing 没有套用 8,000 字符合计预算。

依据：maintenance / finishMemoryLocked。

沿用旧 S1 · Run.kind = handoff · 内部轮次

S1 写交接：利用自己已有的历史，整理一份接手笔记

本次新增，按这个顺序

  1. 交接专用约定：不使用工具、不改文件、不回答新问题；保留未决要求、精确限制与纠正、已验证结论和证据锚点、暂放话题、后台任务 ID / 版本 / 状态；区分事实和猜测。
  2. Core's durable state：当时的 contextLocked(true)，补上最新持久状态与近期消息。

只要求返回 checkpoint 文本；没有强制固定章节或 JSON schema。笔记内容由主模型根据现有上下文生成。

原先有什么 / 完成后去哪

S1 已拥有自己的原生上下文，包括此前普通交流、读取过的文件 / 工具结果，以及压缩后保留内容。较早细节若已不在窗口里，不会因为“写交接”自动重新完整加载。

输出进入 transition.checkpoint，接手提交后也留在旧 Segment；它不是一条 C1 共享助手答复。

Core 保存笔记全文；送给 S2 时只取前 12,000 字符。写笔记和 S2 接手各自重新取一次状态快照，两次内容可能不同。

一份合适的交接笔记应携带哪些具体线索？
示意内容；不是代码强制的固定格式：
- 未决要求：B 要解释取消审批后的恢复路径；来源 msg-B3。
- 约束：只读、不修改文件；原始来源 msg-B1，后续未撤销。
- 已核对：恢复用准确 thread ID；证据为已读的函数与 item 锚点。
- 尚不确定：实际断线时序还没有真实模型回放证据。
- 后台任务：job-1 v1 正在 W1 执行；不要重复派发。
- 暂放话题：C 的发布回滚问题仍待展开；来源 msg-C1。

这是让 S2 快速理解“为什么要做、做到哪里”的模型整理。当前的 jobs / topics / memories 则提供可核对的结构化状态，两者用途互补。

依据：advanceTransition · note、finishRunLocked · handoff。

新建 S2 · Run.kind = bootstrap · 接手成功后再处理成员输入

S2 接手：用笔记与当前快照建立一段新的上下文

本次新增，按这个顺序

  1. 完整 rolePrompt：再次建立分身角色约定。
  2. 接手说明：这是同一共享对话的内部交接，不是新的用户请求；此轮不执行待办，不使用工具。
  3. Previous checkpoint：S1 生成的交接笔记，前 12,000 字符。
  4. Current durable state：重新取 contextLocked(true)，有当前有效记忆、话题、任务与最近 12 条原话。

本轮只回复 HANDOFF_READY；核对成功后 Core 原子更新 current，排队成员消息才以普通续聊形式进入 S2。

原先有什么 / 哪些没有复制

S2 是新的原生 thread，只有原生环境和本次接手材料；没有复制 S1 的每次工具调用、整段文件内容或完整长历史。它也没有继承 W 的执行栈。

接手材料和 HANDOFF_READY 成为 S2 自己的历史。接下来的普通成员轮不会再次装入整套快照。

旧证据仍可通过 shadow_history 查回，但需要模型主动查询；当前输出上限和字面匹配也可能使一次查询不足。

依据：advanceTransition · ready / commit、finishRunLocked · bootstrap。

沿用结果到达时的主 S1 / S2 · Run.kind = result · 内部轮次

主段收 W 结果：只追加这个任务的结果包，再面向成员汇总

本次新增，按这个顺序

  1. 结果通知说明：这是服务数据，不是新用户指令；核对任务版本，不能把过时结果当成完成；向共享聊天总结证据。
  2. 完整 Job JSON：任务 title / prompt / sourceId / version / state，以及 result、resultVersion、结果事件等已有字段。

此处直接发送 Job，不经过 messagePrompt，所以没有自动附加本轮成员消息、记忆增量或完整状态投影；result 也不按投影的 1,600 字符截断。

原先有什么 / 结果怎样转成共享回答

当前主段已经有自己的历史；若是 S2，还已有接手笔记和初始化快照。它从 Job 得知 W 的结论，不会直接获得 W 的全部执行过程。

sourceId 是原始要求的锚点，不是再次附上该消息正文；有必要时可查原话、任务状态或 W 归档。

模型在本轮写出的答复才进入 C1。尽管运行在主 thread，这个 result 轮仍不能修改 Core 记忆、话题或派发任务，因为写工具只接受 kind = main。

共同的“状态快照”，逐个字段是什么

contextLocked(true / false) 都是从 shadow.json 选择一部分字段，再序列化成 JSON。它不会直接把整个文件传给模型。true 只比 false 多一个 recentMessages；W 之外的首轮、CM 和交接都用 true。

字段实际内容范围与更新方式
conversationId / spaceId当前分身对话和所属空间的 ID。用于指明数据归属；不包含整个空间的材料、其他分身聊天或成员档案正文。
memories / memoryRevision当前有效记忆对象，以及全局记忆版本号。条目含 id、text、scope、sourceIds、revision、state、updatedAt；member 条目另有 subjectId。只取 active，按 revision 从新到旧；正文合计最多 8,000 字符，遇到下一项放不下即停止。8,000 不包含 JSON 元数据，版本号也可能大于实际装入条目的版本。

jobs / totalJobs任务对象，含目标、来源、版本、W ID、状态、结果与事件字段；总数含投影中未展示的任务。全部非终态任务 + 最多 8 个终态任务；终态按创建时间选最新 8 个，不是按完成时间。每项 prompt 取 1,200 字符，result 取 1,600；其他字段仍在。
recentMessages

模型“知道可以查”与“已经看过”之间，还有一次工具调用

查询工具返回什么

  • shadow_recall按 query 对记忆正文作不区分大小写的子串匹配，最新最多 50 条，含候选与 forgotten；还返回完整任务列表、话题与当前 revision。按非空文字搜索时，正文已清空的 tombstone 可能匹配不到。
  • shadow_task · status返回当前全部 Job；不套用状态投影中的 1,200 / 1,600 字符截断。
  • shadow_history搜索本分身共享消息与各 thread 的原生 item 归档，含旧段和 W。按文本子串或消息 / item ID 匹配，最新 20 项，每项最多 8,000 字符；没有自动的整段前后文扩展。

哪些轮次能调用

所有新建 thread 都注册相同的 5 个 shadow 工具。Core 对活动轮次开放以上读查询；只有 kind = main 的成员输入轮，才可修改记忆、话题或任务，并进一步核对来源、作者与版本。

因此，“在主 Session 中”不等于“本轮有写 Core 状态的权限”：result / handoff / bootstrap 也会被写工具拒绝。W 同样不能用 shadow_task 再派发 J。

CM、M、交接和接手提示词要求不使用工具；这不是撤销它们的全部原生工具。实际原生能力仍按本机配置与审批规则生效。

Core 以 contentItems: [{type: inputText, text: JSON结果}] 回传动态工具结果，由 Codex 继续工具循环。结果进入调用它的那个 thread；不会向其他 thread 实时广播。另一个 Session 需自己查、等下次快照，或通过专门的结果通知得到它。

依据：dynamicTools / handleTool / toolLocked / historyLocked。当前工具结果的限额与快照不同，不能据“快照有界”推导“全部工具输出都很短”。

原生压缩、换段与重启，对上下文分别做什么

原生压缩：仍是同一个 S1

Core 调 thread/compact/start，没有附上自己的摘要提示词；具体压缩内容与保留规则由 Codex 处理。Core 不会在压缩后自动把完整 rolePrompt / 状态快照重发一遍。

对比换段：S2 的 Core 输入明确包含“角色 + S1 笔记 + 当前投影”，而压缩后的具体窗口不能用这个配方代替说明。

重启恢复：恢复原 ID，不另做一份摘要

Core 调 thread/resume 恢复准确的主段、需要恢复的 W / 活动轮次，显式传入并核对创建时固定的模型设置；由原生恢复该 thread 的上下文，再核对 turn ID 或运行标记。

它不会把整个 shadow.json 重新灌进一个新 thread，也不把“重连”当成“重放用户问题”。磁盘上的共享记录、原生归档和模型当前窗口始终是不同层。

用一条约束检验这个设计：B 说“只解释，不修改文件”。S1 先从原话知道它；W 需要从来源消息、任务 prompt 或查询中得到它；CM 只能看到本次检查材料里保留下来的部分；S2 依赖交接笔记、话题 / 任务状态、近期原话或主动回读。M 应把它视为临时任务约束，而非自动提升成 B 永久不允许修改文件的个人记忆。

依据：context.go · compact / advanceTransition、native.go · restore / reconcileRuns。以上说明输入机制，不承诺模型一定完整保留、正确理解或主动检索每一条约束。

03 / 上下文维护与换段

CM 提建议，Core 选执行边界，Codex 做原生压缩

Core 用原生报告的最近一轮 inputTokens + outputTokens 和上下文窗口估算压力。默认保留窗口的 1/8，CM 检查线是剩余部分的 80%，所以约等于完整窗口的 70%；到 87.5% 会暂缓投入新消息。它不是累计账单 token。

正常续聊 · 0–70%检查区间预留
70%：还需满足间隔与增长条件87.5%：暂缓新输入100%：窗口上限

这是默认参数示意，不是当前模型实际读数。检查至少间隔 15 秒，并以增长水位抑制重复判断；原生不报告窗口时不会猜一个值，继续依赖原生压缩。

compact · 仍然用 S1

在主轮与审批结束的边界调用 thread/compact/start，摘要由 Codex 原生生成。原生也可自行压缩；完成后递增压缩代次、清空旧用量，等新报告。

switch · 交接到 S2

先让 S1 写交接笔记，再创建 S2 接手。收到准确的 HANDOFF_READY 才原子更新 current；随后取消 S1 订阅，不删除原生历史。

① 暂停主段投递新消息继续落盘并排队，独立 W 继续工作。
② S1 写交接原生历史 + 当前持久状态，记录未完成项与来源。
③ S2 确认接手笔记 + 最新状态，先完成内部接手轮。
④ 更新段指针用户输入与任务结果交给当前 S2。

CM 自身看到的是近期消息、未决话题、任务状态和段用量，不是 S1 的整份 transcript。段 ID、压缩代次或消息数变化后，旧建议作废；维护轮默认 90 秒超时，晚到建议忽略。逼近预留区时，CM 失败或输出无效会回退到原生压缩。

与早期设计不同：目前没有“任何情况下都自动救成新段”

交接笔记失败会保留原段并记录错误；S2 接手失败会暂停。源码里没有旧页面所设想的通用“上下文已经溢出后，用外部检查点无模型重建 S2”兜底。DS-Bot 则有硬线/溢出时携带旧笔记和原话的 fallback 路径。两者的恢复可用性不能只按“都能换段”判断。

依据：context.go · maintenance / advanceTransition、native.go · tokenUsage / contextCompaction / finishRunLocked。

04 / 记忆的生成与生效

明确要求直接保存；后台整理只提候选

路径 A · 成员明确说“记住 / 改成 / 忘掉”

  1. 当前主模型识别请求，调用 shadow_remember。
  2. Core 校验活动主轮、来源作者、范围和基准 revision。
  3. 成功落盘后推进版本，模型才能确认保存。
  4. 后续成员轮通过变化增量看到新版本；新段读取当前有效值。

“是不是明确记忆请求”主要依赖主模型遵守提示词；Core 强制校验的是来源、归属和版本，并没有用关键词解析器证明这层语义。

路径 B · 空闲整理 M

  1. 默认闲置至少 45 秒，且水位后有至少 4 条新消息。
  2. 每批最多 20 条，每条截至 2,400 字符；附最多 30 条已有记忆。
  3. 新建短 thread，最多提出 6 个带来源的候选。
  4. 结果格式、来源有效，且记忆版本未变化，才保存候选并推进水位。

4 条按成员与分身消息合计，不是 4 次用户提问。候选可在共享界面与 recall 中看到，但不会自动注入有效记忆快照；需要用户在对话里确认。

记忆如何生效与失效 · 下列按钮是独立示例状态，不会写入真实记忆

范围、可见性和“忘掉”必须分开理解

  • member 表示归属，不表示私密。其他成员不能改写 B 的个人记忆；共享 View 和 recall 仍会返回这些条目，空间成员可读。
  • space 仍保存在当前 shadowId 下。它是这条分身对话中的共享知识，不会自动成为同一空间所有分身共用的数据库；也没有跨空间的统一个人画像。
  • 纠正靠 ID + baseRevision。Core 拒绝过期版本或错误作者；后台 M 遇到版本变化整批不提交，避免覆盖新的明确更正。
  • 忘掉设置 forgotten 并清空当前 text。它保留 tombstone、原始聊天、旧运行记录和原生历史；下一轮提示停止使用旧值。当前没有强制重建 Session 或抹除已进入模型上下文的内容。

没有 embedding、向量数据库或语义召回。状态 JSON 随记录增长，history 查询逐文件扫描；原型目前没有自动保留期或垃圾回收流程。

DS-Bot 的检索

recall 可读整个主题，或对最多 6 个关键词做匹配：优先全部命中，否则按命中数返回，最多 30 条；read_own_chat 提供跨分段搜索和锚点前后文读取。

这条记忆路径也不是向量检索。DS-Bot 的“topic”是记忆文件分类；Team Cross 的 T 是进行中话题状态，两者不是同一种对象。

还有另一套独立的“原生个人记忆”。Team Cross 使用本机有效 Codex home，原生配置中启用的记忆按原生规则加载；它不把自己的 memories 写入原生 MEMORY.md，也不把 P0 私人会话自动 fork 进来。因此“不导入私人会话”不等于“完全隔离个人记忆与工具”。这也适用于新建的 W、CM、M；提示词要求 CM/M 不用工具，并不意味着另外创建了一个裁剪权限的模型环境。

依据：app.go · DefaultDataDir、shadows.go · shadowConfig、store.go · writeAtomic、native.go · archiveLocked、DS-Bot memory.js。

07 / 如何理解“已经实现”

机制已经接通，长期记忆质量仍需要持续验证

已有记录证明的范围

2026-10-21 的实现记录记录了 Codex CLI 0.163.0-alpha.11 / gpt-5.6-luna 的专用会话验证：W 运行时前台能回答、原生压缩、S2 接手、同一 W 晚到结果、记忆纠正/忘掉、准确 thread 恢复与 M 水位。

另有单 Mac 三 Core / TLS 共享作者、送达、同 ID 重发与 MCP 读取验证。该记录对应当时的实现，不是此次重新运行的测试。

尚不能从这些结果推出

默认 CM 阈值已最优、长期对话不会漏项、记忆候选总是准确、全插件/第三方模型组合可用、两台 Mac 网络可靠性，以及 Claude 分身已接入。

当前分身创建入口固定 Codex；CM/M 也可能有原生配置开销。DS-Bot 此次只做源码对照，没有运行模型或对两者做同负载的速度、成本、质量基准。

真正影响下一步工程判断的四件事

  • 自动记忆要不要直接生效。这是“尽量少确认”和“减少错误记忆累积”的产品选择，不是把 45 秒改成 2 秒就能解决。
  • 哪些记忆应跨分身复用。现有 space / member 范围没有形成全局人类画像；引入共享库前要定义归属、可见性与纠正权。
  • 故障时更偏向继续还是等待核对。必须一起考虑文件写入、工具副作用和重复通知，不能只比较恢复速度。
  • 规模增长后的状态与检索。Team Cross 的整份 JSON 重写、逐文件扫描、原生与 Core 两份历史，以及持续增加的短 CM/M thread 都有成本；目前没有长期容量与质量基线。
后续怎么验证，才不会把架构图当成效果证明

固定相同的脱敏对话、模型与配置，回放 A → B → A、成员偏好冲突、纠正/忘掉、长 W 期间换段、回执丢失与重启。先检查错误归属、重复执行与错误送达，再比较未决项保留、召回正确率、延迟与 token。每次只调整一个阈值或提示词，使用未参与调参的保留样本。

现有真实测试降低过 CM 触发线，并在 CM 选择 compact 后显式要求换段，以覆盖两条路径。因此它证明接口与状态链接通，不能证明默认策略在长期真实对话中总能选对时机。完整复验要求见验证契约。

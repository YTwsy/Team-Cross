## 设计结论

普通问答按消息流处理，明确的后台交付才进入 Work 生命周期。新消息持续送入已有 Session，模型负责理解、追问、回复及决定是否派活；Core 保存消息、确定来源归属、可靠投递与发送回复。

与 10 月 25 日基线相比，本方案进一步取消普通补问的 `awaitReply`、隐式 `coordination Job`、条件满足判断和自动结案。它不是在新数据结构中重建一套轻量任务：普通聊天不再承诺逐个问题的严格业务完成状态。需要明确等待、完成条件或后台交付的工作仍由显式 Work 承担。

保留 S/W、跨 Core 收发、准确回传、去重、原生权限和恢复底座；移除认识整理对业务动作的前置阻塞。本次不跟进侧边问答，不引入多级派活树。

## 普通消息与补问

成员连续发出的问题、补充和普通答复进入同一个有序输入流。Core 保留每条消息的稳定 ID、可信作者、原文、顺序、准确来源及回复关系。合批只是把多个输入一起交给模型，不把不同人的要求改写成一个要求，也不把不同消息合成一个身份。

普通补问直接使用既有讨论回复工具。例如 S 在原讨论问同事“超时后是否可能已经写入”，同事答复作为新消息回到当前 S，模型结合原问题继续回答。Core 不要求填写答复条件或下一步，不创建普通协调任务，也不把“已有人回复”解释为“业务条件已满足”。

出站消息的来源、发送回执与执行归属仍需持久保存，以便重启、主会话换段后找回回复目标。已有明确 W 归属的答复回原 W，其余普通输入回当前 S；依据稳定消息关系路由，不另跑分类模型，不用相似文字猜目标。存在多个候选时由 S 利用上下文或澄清处理，不盲目投给某个 W。

普通对话只显示消息事实，如已接收、已投递、已发送回复。有明确 Work 时才显示工作状态；不继续为每句普通补问提供“等待条件满足”和“自动结案”的任务语义。已有本人接回某个讨论问题的处理归属继续生效，不由新消息覆盖。

## 连续输入与原生会话

### Codex 输入方式

- 当前 S 空闲：收集已到达且尚未投递的有界输入批次，通过 `turn/start` 开始一轮。
- 当前 S 有活动轮次：通过 `turn/steer` 追加新增输入，传入准确 `expectedTurnId`，不创建第二个并行 turn。
- 压缩、切段或运行时暂不能受理：保留持久待投递输入，待有效边界继续。
- 原生明确拒绝已过期的 turn：重新读取当前状态，再决定投递方式；网络结果未知时先核对，不自动改走 `start` 重发。

同一 Session 的投递串行化，每次只发送选定的增量批次；后来到达的消息进入下一批，不通过不断重置合并计时而永久延迟。输入体积受上下文预算约束，长材料保留原文与来源入口；不重复注入完整历史、无关空间动态、W 的全部工具日志或自身发言回声。

这取消上一轮讨论中“用户输入与接续分两类队列轮换”的方案。需要模型判断的有效新信息按同一输入顺序进入；W 已写好的对外回报独立走 Outbox，无需先排进 S 改写。

`turn/steer` 的受理不表示模型已经逐条读完或作答。工具执行、审批、模型服务及上下文维护仍可能影响实际响应时间；不承诺零延迟，也不把一个原生 `turn/completed` 当成批次里每条问题均已完成。[Codex 官方协议](https://learn.chatgpt.com/docs/app-server#steer-an-active-turn)

### 与 Claude Channels 的关系

借鉴的是向已有 Session 持续发送事件的模式。Claude Channels 官方文档明确说明：忙时事件排队，下一轮一并处理；发送通知成功只说明写入传输，不能据此认定模型已经处理。Codex 使用自己的 `start / steer` 接口，不使用 Claude 的通知协议，也不因此扩大 Team Cross 的 Claude 接入范围。[Channels 官方投递说明](https://code.claude.com/docs/en/channels-reference#notification-format)

## Work 与回报

S 处理短问题并可直接使用工具；需要独立长调查、修改代码或验证交付时，通过 `shadow_task start` 保存 Job，轮到执行时创建 W。S 派发后简短说明并收尾，Core 不等待 W 完成才继续收发主会话输入。

日常后台流程以 `start / report` 为主，`status / update / cancel / resume` 按需保留。按操作收窄参数，W 内的任务身份与版本由当前 Run 绑定；多来源主回合创建任务时必须明确绑定实际请求，不能机械继承最早或最新一条消息。

| report 意图 | 工作行为 | 对外回报 |
| --- | --- | --- |
| `continue` | 保存已确认进展或检查点，W 可继续调用工具 | 有可公开的阶段答案时，直接按来源发送，不等待整个工作结束 |
| `wait` | 显式 Work 保存确实阻塞的对象与恢复所需信息；原生轮次结束后释放执行槽 | 说明缺少什么；收到真实答复后回原 W 判断和继续 |
| `complete` | 版本有效、完成条件核对通过且无未解决阻塞后，提交结果与依据 | 同次保存固定结果和 Outbox，再独立送达 |
| `fail` | 保存失败事实与已做行动，避免把未完成说成成功 | 发送可核查的失败结果，后续恢复按原工作处理 |

公开回复工具仍可由 W 在执行中直接调用；若正文已经在原讨论实际发布，后续 report 关联原回执，避免再发一份。需要综合判断才交 S；不是把 W 的全部原生文本自动广播为公开消息。

业务完成、通知送达与认识摘要整理分别记录。通知暂未送达或摘要整理失败不回滚已确认的工作结果。个人会话委托仍通过已经绑定的 MCP / Hook 路线回传，不猜“最近会话”，不新增自动启动接收模型的机制。

## Session 与文件范围

S 在首次需要行动的输入到来时创建，后续话题和普通补问复用当前段。W 在显式后台工作获得执行位置时创建，等待后复用原 W；S 换段不改变 W 的身份。CM、M 和原生换段沿用现有机制，本次不增加新的维护会话。P0 是外部已有个人会话，发生委托时绑定回传，不自动导入其私人历史。

Core 文件保存消息、输入投递与动作回执、工作事实、返回路线和 Outbox；原生 Session 保存各自的模型与工具历史；项目目录保存真实交付物。Session 只带相关事实、增量和可回读的来源。具体条带和存储位置见 HTML，不另建每任务 Markdown 或第二套轻量等待账本。

### 比较判断

附件对“业务完成不能被认识整理阻塞”和“不要重建第二套等待系统”的判断继续成立。其主要取舍是保留内部任务模型，先减轻模型调用协议；本次则减少普通聊天的产品承诺，使普通补问退出任务生命周期。两者不是同一种实现换了工具名。

最新目标更符合本次对简单交流的要求，但工程上并不必然更少改代码。当前依赖路由、待答列表和原会话问题回传围绕 Job 构建；若删去普通 Job 后仍要求逐个问题的条件验收、完整待办和自动结案，就会把附件警告的第二套任务系统重新做出来。应将这些严格语义限定在显式 Work，普通路线只补足消息关联和可靠收发。

DS-Bot 可借鉴未读输入合批、消息自动带来源关系、长工作不占群聊、执行中直接报告。它自身仍维护 work、父子关系、等待与请求幂等，因此不能作为“所有持久状态都可以删除”的依据。其向等待本工作结果的上游 Bot 发消息限制也不照搬；Team Cross 向委托者补问属于正常澄清。

本次以最新方案作为目标，以附件作为现有依赖与迁移风险清单。附件提出先收尾工作区代码的步骤不在此次文档提交中执行；旧报告中的百分比降幅、历史验证和成本推断不自动作为新方案的验收结论。

## 推进顺序与验收范围

1. 先验证同一 S 的输入适配：批量 start、活动 turn 的 steer、turn 恰好结束时的竞争、原生明确拒绝与未知结果分别处理。多人消息和两条独立委托混入同一轮时不得串作者或回传目标。
2. 普通回复与补问退出业务任务化；解除认识 JSON 对直接回复的成败绑定。验证回复关系在重启、主会话换段、本人接回后仍准确，且不恢复语义条件与自动结案。
3. Work 收敛到 start / report，阶段回报直达；业务完成与 Outbox、摘要整理分别推进。验证取消或目标变化后的旧版本不能继续形成有效结果，已发布正文不会再被结果通知重复发送。
4. 按[验证契约](../sources/validation/test-gates.md)执行实现对应门槛，再用专门测试会话与仓库、`gpt-5.6-luna` 进行真实产品路径验证。记录投递至原生受理、可见回复延迟、轮数和重复回报，实测后评价收益，不预设降幅或零延迟。

本次保留准确作者与来源、原生权限和审批、独立消费者水位、发送前落盘、去重、Outbox、明确 Work、已有换段和记忆维护。延后侧边问答、普通关注的独立观察流水线、多级派活树、复杂 watch、多认识联动以及超时自动搬迁在途原生回合。
